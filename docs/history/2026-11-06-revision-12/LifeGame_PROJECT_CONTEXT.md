## 3. Безопасный процесс разработки

1. Русский язык, только согласованная задача по актуальному исходнику.
2. **Сейчас по умолчанию обсуждение → отдельное согласование → отдельная реализация**; прежнее поручение на большой облачный аудит было историческим и **не** разрешает новые правки. Для утверждённой задачи с изменением HTML — **один скачиваемый самодостаточный `.md`-промпт Cline** с точными уникальными якорями **НАЙТИ → ЗАМЕНИТЬ / ДОБАВИТЬ / УДАЛИТЬ → ПРОВЕРИТЬ**, предварительным поиском уже внесённой реализации и явными условиями остановки. Применять к текущему локальному файлу, не к старым срезам; номера строк — ориентиры.
3. До правок проверить все якоря и отсутствие уже внесённой реализации. Отсутствие/неоднозначность — остановиться, не угадывать.
4. При задачах, **изменяющих index.html**, создать **ровно одну новую** копию `backups/index-YYYY-MM-DD-HH-mm-ss.html`, не перезаписывать. **Перед записью HTML** проверить её существование, размер и **побайтовое совпадение исходнику**. SHA-256 полезен для сверки с отчётами, но не заменяет побайтовый контроль. При любой ошибке — остановиться; старую копию не переписывать.

6. UTF-8, кириллица, без форматирования остального файла, зависимостей, рефакторинга и самовольной чистки CSS/старых функций.
7. **Без отдельного разрешения не запускать браузер, приложение, JavaScript, автоматические тесты и стенды**; не публиковать и не менять среду. 8. Не очищать localStorage, не менять основной ключ/ID, не сбрасывать пользовательский прогресс, не удалять файлы и не публиковать без разрешения.

Экспорт: `{app:"LifeGame",version:1,createdAt,data}`. В data — state, включая widgets, dayGraph, **happiness** и keyActions. Версия оболочки остаётся 1. **Отдельный `lifegame_happiness_200_messages.json` не включается в пользовательский экспорт**, потому что это справочник вымышленных реплик, а не прогресс. Импорт заменяет всё, не объединяет: normalize → подтверждение → ensureDay → normalize, focus.notified=true, запись, очистка очереди наград, переход на hero.

Полный сброс требует СБРОС, создаёт emptyState и восемь стартовых блоков; возвращает два системных виджета. **Обнуляет также `state.happiness` (коллекцию, чат, виртуальную очередь и режим), но не удаляет внешний файл базы реплик.** Маркер демо не удаляется, поэтому повторное появление примеров не гарантируется.

Поля state: soundEnabled; motivationEnabled/motivationText; widgets; **dayGraph**; **happiness**; keyActions; blocks; goals; diamondRecords; tasks; quests; bonuses; completions; calendarEntries/calendarCompletions; purchases; treats/treatUses; focus; dayPlans/dayPlanDate.

- emptyState — старт.
- normalize — clone, normalizeKeyActions, normalizeWidgets, **normalizeDayGraph**, **normalizeHappiness**, миграции/проверки остальных сущностей и балансов. Если поля happiness нет в старом сохранении, добавляются значения по умолчанию без очистки других разделов.

## 6. Валюты, уровень, начисления

Монеты: earned=sum(completions.reward), spent=sum(coins purchases.price), balance=earned-spent. Алмазы аналогично diamondRecords.amount и diamonds purchases.price. Обмена нет.

Уровень floor(earned/1000)+1, прогресс earned%1000. Покупки уровень не снижают; отмена заработка может снизить. Опыт отдельной сущностью отсутствует.

Нельзя отменить заработок с отрицательным итоговым балансом: сначала возврат покупок. Это действует и при уменьшении времени ключевых действий, отменяющем дневную выплату. Но удаление всего ключевого действия сохраняет монеты и поэтому допустимо при потраченной награде.

Префиксы completions.taskId:
- обычное задание: ID;
- финал: quest:<questId>;
- шаг: quest:step:<questId>:<paymentId>;
- этап: quest:step:stage:<questId>:<stageId>;
- календарь: calendar:<entryId>;
- бонус: day-bonus:<localDate>;
- ключевое действие: key-action-day:<actionId>:<YYYY-MM-DD>.

ID и фактические суммы постоянны. Не переименовывать префиксы без миграции потребителей. normalize запрещает повтор taskId+date.

```js
  ],
  favorites: []
}
```

Это стартовый состав, не принудительный состав каждого сохранения. items задаёт сборку и порядок; showInDay — размещение. favorites независимы от items. Данные функций отдельно: state.keyActions, state.focus, state.dayGraph и **state.happiness**; «Первый шаг» не имеет сохраняемых ответов. Справочник 200 виртуальных реплик отдельно от state.

Реестр:
- keyActions, «Ключевые действия», ◎, системный, доступен, категория «Фокус и время», placements widgets/day, render keySection(true).
- focus, «Время для важного», ⏱, системный, доступен, та же категория/размещения, render focusCard(true).
- dayGraph, «График дня», ▦, несистемный, **доступен**, «Фокус и время», placements widgets/day, render dayGraphCard().
- firstStep, «Первый шаг», ➜, несистемный, **доступен**, «Фокус и время», placements widgets/day, render firstStepCard().
- **happiness, «Игра в счастье», ☀, несистемный, доступен, «Душевное состояние», placements widgets/day, render happinessCard() (компактная карточка; полная игра в отдельном окне).**
- challenge, «Вызов себе», 🔥, несистемный, недоступен/«Скоро», «Вызовы и цели», render=null. Описание «Один вызов. Один срок. Твой ход.», пояснение «Дело, срок и добровольная ставка на своё решение». Механика НЕ реализована; подробные правила ставки, срока и результата ещё нужно согласовать, не восстанавливать догадками.

Операции:
- addWidget добавляет только доступный ID без дублей, showInDay:false. Повторное добавление не сбрасывает инструмент.
- setWidgetDay меняет только размещение добавленного доступного виджета с поддержкой day.
- removeWidget удаляет item, тем самым убирает из обоих экранов, сохраняет данные функции и избранное; подтверждение особенно явно отделяет скрытие keyActions от очистки данных.
- moveWidget переставляет items; day фильтрует этот же порядок. Порядок каталога не определяет порядок сборки.
- Неизвестные ID сохраняются: заглушка в сборке, перестановка/удаление доступны, неизвестное размещение не запускается.
- renderDayWidgets ничего не рисует для отсутствующих/скрытых/недоступных инструментов.
- На основном экране по одной рабочей панели каждого инструмента, не дублировать их жёсткими вызовами.

Миграции normalizeWidgets:
- widgets отсутствует → текущий стартовый состав.
- v1 сначала проверяется прежняя структура, существующим item назначается showInDay только для focus; отсутствующий focus добавляется первым, favorites=[], затем v2.
- v2 проверяется (boolean showInDay, favorites с уникальными ID); отсутствующий keyActions добавляется первым, затем v3. Остальные элементы/порядок/favorites/showInDay сохранены. Ранее удалённый focus на этом переходе НЕ восстанавливается.
- v3 принимается как есть, в том числе items:[], отсутствие обоих системных и неизвестные ID. Нельзя восстанавливать стартовый состав при каждом запуске. Неизвестная версия/повреждение — ошибка.

Каталог: категории включают Все/Фокус и время/Вызовы и цели/**Душевное состояние**, флажки «Только системные» и «Только избранные», счётчик/пустое состояние. Условия применяются совместно. Сортировка: системные → избранные внутри группы → название ru → ID. Таймер не закреплён поверх алфавита навсегда: системных два. Несистемные `firstStep`, `dayGraph` и **`happiness`** доступны для добровольного добавления; `challenge` по-прежнему недоступен.

Фильтры widgetCategory/widgetSystemOnly/widgetFavoritesOnly только в памяти вкладки, переживают переходы и render, не reload. Фильтр вызывает локальный draw без записи. Звёзды сохраняются в favorites через widgetChange и вызывают общий render. Недоступный challenge можно отметить звездой, но не добавить.

## 8. Ключевые действия: механика и важные различия удаления

До трёх active, не сбрасываются ежедневно. Новый слот после закрытия/удаления. Один инструмент в двух размещениях.

keyActions.version=1, массивы actions/conditions/entries.

Действие: стабильный id; name обязательное до 120; meaning необязательное до 300; criterion обязательное до 300; minutes целые 1–180; reward целые 0–100000; createdAt ISO; createdLocal местная YYYY-MM-DDTHH:mm:ss; status active/completed/archived; closedAt местное либо null; необязательное deleted boolean.

Условия: actionId, date, minutes, reward; одна пара actionId+date. Запись: id, actionId, date, minutes 1–180 за запись, createdAt ISO. Несколько записей в день допустимы.

Создание/изменение/время/закрытие через transact(...,false), перестановка keyMove через (...,false,true). Ориентир/награда нового действия действуют сразу. При редактировании сегодняшние условия сначала фиксируются, а настройки обновляются для следующих дней; даже без времени сегодня условия не меняются. Название/смысл/критерий меняются сразу.

Время только вручную за сегодня. Формы проверяют день и актуальный статус внутри транзакции. Прошлое время и время закрытых действий доступны только для просмотра. Таймер НЕ связан с этой механикой.

keyReconcile: при достижении сохранённого ориентира одна выплата, reward=0 не создаёт completions. Поля связи keyActionId/keyActionDate. Превышение не даёт второй выплаты. Пока достижение сохраняется, ID выплаты остаётся прежним. Уменьшение ниже ориентира снимает выплату; защита потраченных монет отклоняет всю транзакцию без частичных изменений.

Закрытие не даёт монет/алмазов. Связи с целями блоков нет.

ОБЯЗАТЕЛЬНО различать:
1. Завершить — completed, история и время сохраняются.
2. Убрать без завершения — archived, история и время сохраняются.
3. Удалить действие — deleted=true, active переводится в archived; удаляются ВСЕ его entries за все даты. У закрытого прежние status/closedAt сохраняются. Карточка скрыта из активных и истории; монеты сохранены.
4. Удалить все ключевые действия — ввод УДАЛИТЬ, помечаются все actions, entries=[], остальные данные приложения не затрагиваются. Это не удаление виджета.
5. Убрать виджет из сборки/Конструктора — только скрыть, ВСЕ данные ключевых действий сохранены.

Для deleted остаются технические actions и conditions ради проверки выплат. Фактическое время не копируется в скрытый архив. normalize удаляет оставшиеся entries deleted как согласованную миграцию. Проверки существования действия/условий, точных taskId/даты/суммы и дублей сохранены. Только требование достижения по удалённому времени и обязательность выплаты для deleted не применяются. Для остальных строгая двусторонняя проверка сохраняется. deleted с active недопустим. keyActive и keyReconcile запрещают обычные мутации deleted.

После удаления время/число достигнутых ориентиров уменьшается, но earned и уровень нет. Можно получить 0 минут и положительный заработок. Новые действия имеют новые ID и могут заработать свою награду — следствие принятого правила, не исправлять самовольно.

Местные createdLocal/closedAt не сравниваются как надёжная хронология. inLifetime в проверке данных требует существующий action и validDate, не ограничивает местными датами создания/закрытия. История показывает последние семь календарных дней: пустые дни только внутри отображаемого срока, реально сохранённые условия/записи показываются и вне формальной границы. Сдвиг календарный, не 86400000 мс. Старые даты через текущий пояс не пересчитывать.

Интерфейс:
- обычный заголовок виджета, системный бейдж, меню размещения ⋯ отдельно;
- общий итог «Главному сегодня» включает все фактические сегодняшние entries, включая закрытые действия;
- компактные строки, прогресс, галочка ориентира; ＋ прямо на панели открывает минуты с названием действия;
- прямой ＋ сбрасывает keyRoute/keyPending: сохранение/отмена/Escape оставляют на исходном day или widgets, без лишнего окна;
- строка открывает просмотр, не редактор;
- явная «Управление действиями →» внизу всегда, даже без active/при истории/при !healthy (просмотр разрешён);
- пустая панель также имеет «＋ Добавить действие»;
- в управлении стрелки ↑↓ переставляют только соседние active, закрытые/удалённые остаются на местах;
- история свёрнута; сегодняшняя запись имеет меню исправить/удалить; закрытая карточка имеет меню удаления;
- массовая очистка сейчас видна в управлении уже при одном элементе — принято оставить, будущую компоновку не менять без задачи.

keyDialog ленивый, keyRoute/keyPending/keyFocus и keyExpanded в памяти. keySuspend/keyReturn/keyMenu обеспечивают возврат из editor/menu. Форма с ошибкой остаётся открытой. Запасной фокус после закрытия — .key-manage-button. Условный keySync в конце render обновляет окно независимо от размещения, а НЕ из keySection. Не дублировать обработчики и не создавать несколько копий функции ради разных экранов.

## 9. Обычные задания и бонус дня

Задание: name до 120, reward 1–100000, block ID, favorite, weekdays и необязательный **`goalId: string | null`** — ссылка на одну существующую цель **того же блока**. В старых сохранениях отсутствие `goalId` нормализуется в `null`; неверная или чужая связь отклоняется валидатором. []=once, выбранные дни 1–7=daily. Пресеты разовое/ежедневно/будни/выходные. Новые не включаются автоматически. В форме создания/редактирования вопрос «Этот шаг ведёт тебя к цели?» с добровольным выбором цели; смена блока сбрасывает несовместимую связь.

Повторяемые используют постоянный inDayBuilder и расписание; разовые — dayPlans[today]. ensureDay пересобирает сегодняшний план. Выполненное в другой день разовое не включается как сегодняшнее. Избранное не включает в план.

completion различает фактическую историю. При once↔daily старые записи без taskType получают legacy, включается historySeparated; не удалять границы. Редактирование сохраняет ID и прошлые выплаты. **Текущее штатное архивирование** убирает ID из сегодняшних/будущих планов и сохраняет монеты/историю; восстановление не включает задание в Конструктор автоматически. Старое физическое удаление карточек — историческая механика, см. раздел 29.

MIN_DAY_TASKS=3, DAY_REWARD=100: минимум три обычных задания сегодняшнего плана, ВСЕ выполнены сегодня. Квесты, календарь и ключевые действия не заменяют задания. Бонус содержит `sourceCompletionIds`. `reconcileDayBonus` обеспечивает сверку с исходными фактами выполнения; финансовую историю не переписывать вручную. **Принятая политика гибкого плана (AUD-10-03):** если одиночное архивирование **невыполненного** задания из сегодняшнего плана оставило минимум три задания, все выполненные сегодня, и бонус за сегодня ещё не начислен, стандартные +100 выдаются **сразу после успешной транзакции**. Иные архивные операции не запускают начисление. Полученный бонус не отзывается из-за восстановления или добавления новых заданий в план; один бонус за дату, исторические дни не пересчитывать. Подробности в разделе 30.

## 10. Блоки, смысл и цели

Восемь стартовых: Душевное состояние; Физическое состояние; Знания, навыки, опыт; Ресурсы и материальное; Окружение и отношения; Наполнение и организация; Обстоятельства; Исключить.

**Актуальное дополнение UX-06:** у блока есть редактируемая **краткая подпись `subtitle` до 120 символов**, отличная от `meaning`; 8 стартовых подписи проставлены по `block-0`…`block-7`. Под названием при наличии показывается подпись; редактирование через «Переименовать», необязательное поле также в создании. Строка `""` сохраняет намеренно пустое значение. Действующий порядок экрана и точные подписи — в §32, а старые упоминания заголовков «ЦЕЛИ»/«ЗАДАНИЯ» ниже в этом разделе — **историческое описание до UX-06**.

Создание, чтение, редактирование блоков с постоянными ID, name до 120. **Вместо прежнего штатного удаления** применяется архивирование `block.archivedAt`, при котором блок, его цели и задания сохраняются канонически. Его задания исключаются из планов сегодня и в будущем, `inDayBuilder=false`; восстановление не возвращает их в Конструктор автоматически. Денежные и алмазные журналы, квесты и покупки не трогаются. Старое описание физического удаления относилось к версии до архива v1.

**Текущий интерфейс внутри открытого блока после UX-06:** смысл/его карточка → **все активные цели** компактными карточками → полноширинная кнопка **«+ Добавить цель»** → полноширинная **«+ Добавить задание»** → обычные задания и выполненное; заголовки «ЦЕЛИ»/«ЗАДАНИЯ» **удалены только здесь**. До содержания расположены верхняя навигация, имя, необязательная видимая подпись и раскрываемая панель настроек. Сортировка задач включается под ⚙ и завершается «Готово». `meaning` до 2000, без награды, внешние пробелы `trim`. В одном блоке допустимо **любое количество активных целей**; ограничение «одна цель на блок» снято из создания и валидации. Цель: `name` до 120, `diamonds` 1–100000, `completedDate`; достижение связывается с `diamondRecords(goalId,amount,date)`. Отмена достижения больше не блокируется наличием других активных целей, но прежняя защита от отрицательного баланса алмазов остаётся. Удаление активной цели не удаляет задания, а очищает их `goalId`; при достижении цели связь и читаемая плашка «Цель: название · достигнута» остаются. Ни выполнение связанного задания, ни наличие связи не завершают цель автоматически и не добавляют награды. Заголовки разделов **без числовых счётчиков**; повторная строка «Заданий: N · На сегодня: N» под названием открытого блока удалена, при этом счётчики общего списка блоков сохранены. Компактные карточки сохраняют названия, награды, меню, выполнение/отмену и управление Конструктором дня.

## 11. Квесты

**Архив v1:** одиночное и массовое архивирование квестов сохраняет ID, прогресс, `stepHistory`, этапы и записи выплат. Восстановление возвращает карточку без перерасчётов и без автоматических наград; исторические слова «удаление квеста» относятся к прежней реализации.

counter/stages, тип после создания не меняется. CRUD в исторической терминологии, `favorite`, `showInDay`; в текущем UI для удаления из активных используется архивирование, сохраняющее монеты и прогресс. Черновики двух вариантов в сессии формы сохраняются при переключении типа.

counter: target/step 1–1000000, reward 1–100000, stepReward 0–100000. После первого плюса started=true, target фиксирован даже после отката к нулю. Будущие шаг/награды меняются. stepHistory хранит from/to/ссылку оплаты/время. Минус отменяет последний фактический шаг, а не текущий step. Финал при target, отмена ниже target снимает финал. Старый legacy-прогресс без истории произвольно не откатывается.

stages: 2–50 постоянных ID, любой порядок выполнения. До старта состав/порядок меняются; после старта зафиксированы, будущие названия/награды редактируются. paidReward/completionId/completedAt/completedDate фиксируют фактический этап. Ноль за этап допустим без монетной записи. Последний этап выдаёт этап+финал; отмена снимает фактические оплаты. normalizeStages вычисляет progress/target и проверяет связи. expandedStages только в памяти.

Финальная награда обоих типов минимум 1, не обещать нулевой финал по старым общим формулировкам.

## 12. Календарь, магазин и общие истории

**Архив v1 для бонусов магазина:** одиночное и массовое архивирование, в том числе купленных карточек, сохраняет `purchases`, исходную валюту/цену и другие исторические записи. Архивирование **не возврат покупки** и не начисление/списание средств; восстановление не повторяет покупку. См. раздел 29.

Календарь отдельный от tasks: понедельник, 42 ячейки плюс заголовки, неинтерактивные пустые; По дням/Все, показать прошедшие. Entry: id/name≤120/date/time?/note≤1000/reward 0–100000/favorite/completionId. Сортировка невыполненные → избранные → время (без времени в конце).

Сегодня автоматически показывается в day. Выполнение создаёт calendarCompletions; при reward>0 также completions с coinRecordId; ноль — факт без монет. Дата факта — день выполнения. Выполненным меняются название/заметка, не плановая дата/время/награда до отмены. Невыполненные переносятся на сегодня. Удаление выполненной карточки сохраняет факт/монеты и предупреждает, что отмена через карточку после удаления недоступна.

Бонусы-магазин: name≤120, description≤300, currency coins/diamonds, price 1–1000000, favorite. Одна активная покупка на карточку. purchase хранит снимок name/price/currency/bonusId/createdAt. Редактирование карточки не меняет покупку; возврат фактической суммы/валюты. **Архивирование карточки не удаляет `purchase` и не возвращает потраченную валюту**; прежнее физическое удаление карточок — исторический вариант до архива v1. История — действующие покупки, отменённые удаляются.

### 15.1. Экраны и жизненный цикл

- Главная ведёт на прежнюю страницу `aiPreview` через `aiPreviewEntry()`; дополнительной нижней вкладки нет. Название интерфейса — **LifeGame AI**, пометка «Тестовая версия».

- При переходе chat ↔ settings текущий диалог, черновик, ключ и разрешения сохраняются в пределах сессии; при уходе из AI-раздела незавершённый запрос отменяется. Поле ввода остаётся доступным при длинной истории, используется адаптация к `visualViewport`; сообщения прокручиваются отдельно.
- Компактные локальные переключатели разрешений и 18+ (с областью касания от 44 px); динамическая перерисовка пытается восстановить клавиатурный фокус без ненужной прокрутки.
- Ответы модели безопасно форматируются ограниченным Markdown (абзацы, жирный, простые списки, заголовки, inline code) через DOM API и текстовые узлы, без исполнения HTML, `innerHTML` или внешней библиотеки. Содержимое ответа хранится исходным текстом, форматируется только отображение.

### 15.2. Провайдеры и временная сессия

- **BotHub:** фиксированная база `https://openai.bothub.chat/v1`, динамические модели `GET /models`, чат `POST /chat/completions`, Bearer-заголовок.
- **Google Gemini:** фиксированная база `https://generativelanguage.googleapis.com/v1beta`, список моделей с пагинацией и фильтром поддержки `generateContent`, `POST /models/{model}:generateContent`, ключ в заголовке `x-goog-api-key`.
- Работа через браузерный `fetch`; без серверного прокси и внешних зависимостей. Модель выбирает пользователь, используется личный API-ключ (BYOK). Возраст — **18+**, явное подтверждение для закрытого теста.
- `ai` — временный объект в памяти текущей вкладки, **не часть `state`**: провайдер/модель, ключ, история, черновик, разрешения, предпросмотр/подтверждённый контекст и запрос. Ключи, чат, разрешения, просмотр не писать в `localStorage`, `sessionStorage`, JSON-экспорт или URL.
- «Новый диалог» очищает переписку; «Отключиться» очищает ключ/модель/историю/разрешения; новая модель или провайдер — новая изолированная сессия. При перезагрузке временные данные исчезают.
- Запрос ограничен по длине сообщения (2000 символов), числу завершённых пар истории (12), лимиту генерации (1024 токена) и тайм-ауту (60 секунд) по отчёту реализации. Завершение асинхронных запросов защищено `AbortController`, идентичностью текущего запроса/сессии; старые ответы не применяются. Отмена в браузере не гарантирует отмену серверной обработки/счёта.
- Адаптеры возвращают текст и информацию об усечении: `finish_reason: "length"` BotHub, `finishReason: "MAX_TOKENS"` Gemini или локальный предел **12 000 символов**. Предупреждение показывается пользователю и не передаётся модели как текст истории. Некорректные схемы ответов имеют отдельную классификацию, не замаскированы под CORS по отчёту Cline.

### 15.3. Характер ИИ и разрешения

- Один `AI_SYSTEM_PROMPT`, общий по смыслу для обоих API: BotHub `role:"system"`, Gemini `systemInstruction`. Философская основа: **«Смысл жизни — во всём, что даёт желание жить»** как идея для исследования, не догма. Партнёр в размышлениях, целях и развитии; без навязанной продуктивности, без заявлений о выполненных действиях и без отдельных переключаемых персон.
- Режим **строго read-only**: ИИ не создаёт/редактирует/удаляет задания, цели, квесты, покупки, планы; function calling и инструменты записи не подключены.
- Четыре независимых разрешения, **по умолчанию выключены**: блоки времени; цели; задания; квесты. Разрешение 18+ не равно разрешению на персональные данные.
- `buildAiContext()` формирует на каждый запрос минимальный whitelist разрешённых полей: блоки — имя/порядок; цели — имя/active/achieved; задания — имя, тип/дни, текущий статус, избранность и применимый признак сегодняшнего расписания; квесты — имя, тип, прогресс/цель, этапы и их статусы. Название связанного блока показывается только при разрешении «Блоки».
- Финансовые записи, суммы наград, покупки, балансы, календарь, мотивация, ключевые действия, таймер, виджеты и полный `state` не передаются. `completion()` допускается для вычисления статуса, не для пересылки записи начисления. Контекст структурно отделён от системной инструкции, названия сущностей — недоверенные данные.
- Актуальность: `loadLatest()` перед сборкой, `serializeAiContext()` общий для предпросмотра и отправки. Персональный JSON ограничен **10 000 символами**, сокращение — целыми записями, с числом пропусков. Лимит относится к JSON-контексту, не к полному HTTP-телу.
- Отдельные `ai.preview` и `ai.confirmedContext`: пользователь явно нажимает «Подтвердить передачу этого контекста». Простое открытие предпросмотра или двойная отправка не заменяют подтверждения. При изменении передаваемой строки JSON подтверждение становится неактуальным, отправка блокируется до нового подтверждения; черновик не теряется и автоповтора нет.
- Любое изменение прав отменяет текущий запрос, очищает историю, предпросмотр и подтверждение, начинает новый диалог. Отзыв действует на **будущие** запросы, не стирает уже переданные провайдеру данные.

### 15.4. Безопасность и известные границы

- Ключ в браузере доступен JavaScript-коду с теми же полномочиями и потенциально расширениям; временная память **не эквивалентна серверному секретному хранилищу**. Публичный выпуск с браузерным BYOK нельзя считать защищённым решением без отдельного архитектурного пересмотра.
- Prompt injection через недоверенные названия сущностей и несовершенное следование модели системному промпту нельзя исключить полностью. Конфиденциальность и хранение провайдерами — отдельные условия их API.
- Сети/CORS/регионы/тарифы/квоты/модели изменчивы. BotHub и Gemini проверялись вручную пользователем на реальных сообщениях; никакие сетевые запросы Cline в ходе правок не запускал.
- Статический аудит 8В до финальной полировки обнаружил **P0=0, P1=0, P2=2, P3=2, ARCH=4**, итог B (неблокирующие проблемы). Затем шесть точечных исправлений реализованы по отчёту Cline и приняты пользователем после **25 ручных проверок**. Особый остаток: malformed API JSON/неожиданные структуры проверены **только статически**, отдельные контролируемые динамические проверки не проводились. Статический аудит не является penetration test и не гарантирует полную безопасность.
- `go()`/`syncDay()` и независимый таймер могут менять `localStorage` по прежним механикам при смене дня; это не вызов `transact()` непосредственно из AI-ответа. Не обещать абсолютное отсутствие каких-либо записей во время открытого AI-экрана.

### 19.1. Детали сортировки

- Для блоков одна временная UI-переменная `blockReorderMode`; порядок сохраняется перестановкой объектов в `data.blocks`, без `sortOrder`.

Завершённые остаются на местах и игнорируются при поиске следующего видимого соседа. Текущий порядок массивов учитывается в Конструкторе дня.
- Перестановки/перенос реализованы через `transact(change,false,true)` для исключения сопутствующих пересчётов и наградных эффектов. При переносе из блока открывается новый блок, из Конструктора дня перехода нет.

### 19.2. Подробности массового удаления

- Режим отдельный от сортировки, включает также завершённые карточки. В заданиях область — текущий или все блоки. В бонусах «Выбрать всё» учитывает текущий фильтр валюты; смена области/фильтра сбрасывает выделение.
- JSON-оболочка остаётся `{app:"LifeGame",version:1,createdAt,data}` и содержит весь state на момент до удаления. Скачивание через браузер, затем ручное подтверждение «Я сохранил JSON-копию», затем отдельный текст `УДАЛИТЬ N`. Сам браузер не гарантирует факт физического сохранения файла — это подтверждает пользователь.
- Перед операцией снова сверяется `snapshot`, текущее хранилище, выбранные ID и их область. Удаление одной транзакцией `transact(change,false,true)`; задания удаляются из `tasks` и `dayPlans`, квесты — из `quests`, карточки бонусов — из `bonuses` **без удаления** `completions`, `purchases` и `diamondRecords`.
- Удаление ранее купленной карточки не означает отмену покупки. Позднейший возврат использует исторические `purchase.price` и `purchase.currency`; удалённая карточка не восстанавливается автоматически. Проверка пользователем: JSON-копия создаётся и восстанавливается; начисления/покупки остаются.

### 23.1. «Мой маршрут» — **ИСТОРИЯ, позднее полностью удалён 6 ноября 2026**

> Всё нижеследующее в этом подразделе — **описание прежней реализации, не действующие требования**. Удаление A–W принято; актуальные функции и единственный совместимый редирект см. §35. **Не возвращать маршрут по старым спецификациям.**

- Отдельная страница `myRoute`, временный черновик `routeDraft` **только в памяти вкладки**; не создавать постоянную сущность маршрута/желания и не менять основной `state` ради черновика.
- Три входа: «Не знаю, чего хочу», «Знаю, чего хочу», «У меня уже есть цель». Выбор ответов выделяется золотой рамкой/галочкой; основная кнопка действия визуально отличается; есть компактное название этапа.
- Принятое упрощение: после желания переход непосредственно к вопросу о личном смысле; при выборе существующей цели — сразу к первому шагу; предпросмотр и начало сохранения объединены в один экран. Удалены дублирующие решения. Пропуск смысла очищает временный текст. Явное завершение без выполненных сохранений не требует лишнего подтверждения; при частичных сохранениях защита остаётся.
- Сохранение смысла, цели и задания происходит **отдельно через штатные формы**, с реальными подтверждениями и проверками. Частично сохранённые объекты остаются; не обещать атомарный «маршрут».
- Маршрут учитывает **несколько активных целей** блока; пользователь выбирает конкретную или предлагает новую. При создании задания из маршрута выбранную цель можно предварительно предложить, связь добровольна и может быть снята.
- LifeGame AI можно открыть добровольно; текст обсуждения пользователь переносит/подтверждает сам. Маршрут не расширяет четырёх AI-разрешений, не меняет системный промпт и не отправляет данные автоматически.
- В настройках галочка **«Показывать „Мой маршрут“ на главной»**, по умолчанию включена; отдельный ключ `lifegame-route-entry-visible-v1` не входит в JSON прогресса. Скрытие кнопки не удаляет функции или игровые данные.

### 23.2. Несколько активных целей и связь с заданием — принято

- В одном блоке может быть несколько активных целей; `goalForm()`, `normalize()` и `renderBlocks()` учитывают это. Каждая цель сохраняет собственный ID и обычную награду в алмазах; достижение и отмена остаются ручными, со старой финансовой защитой.
- У задания допускается только **одна необязательная связь** `goalId: string | null` с существующей целью **того же блока**. Старые резервные копии без `goalId` совместимы; недопустимую ссылку не считать валидной.
- В форме задания: вопрос **«Этот шаг ведёт тебя к цели?»** с галочкой и выбором цели. Для обычного нового задания связь по умолчанию выключена; при смене блока несовместимая ссылка снимается.
- Удаление активной цели снимает ссылки `goalId` у соответствующих заданий, **не удаляя сами задания**. Достигнутая цель сохраняет связь и текстовую пометку о достижении. Завершение задания не завершает цель и не меняет награду.
- В карточке `taskCard()` показывается понятный тег **«Цель: название»**, для достигнутой — **«Цель: название · достигнута»**, одинаково в блоке и Конструкторе дня. Эмодзи `🎯` в этой метке убрано.

### 25.2. Режимы, честность виртуальных игроков, тайминг и пауза

- `state.happiness.mode`: **`solo` по умолчанию** или `virtual` по переключателю в настройках. Игроки названы **вымышленными**, а не настоящими подключёнными пользователями. Реальной сети общения или взаимодействия с LifeGame AI нет; готовые сообщения выбираются из базы.
- Очередь: **пользователь → первый виртуальный игрок через 5 с → второй ещё через 10 с → пользователь**. Во время ожидания у текущего игрока видны три анимированные точки; ввод следующего хода на время круга блокируется. Ответы заранее выбираются попарно, с разными именами; использованные ID учитываются, когда список исчерпан — повторения возможны.
- `happinessSchedule()`/`happinessAdvance()` используют сохранённый `pending.dueAt`: закрытие модального окна не останавливает ход, а после возвращения/перерисовки очередь доводится до актуального состояния. **Переключение в одиночный режим сбрасывает только незавершённый `pending`, не историю и не коллекцию**; чужие сообщения скрываются в личном просмотре чата.
- Текст **«Пауза»** распознаётся как особый ход (включая завершающие пробелы/пунктуацию); он присутствует в чате, **не добавляется в личную коллекцию**. При виртуальном режиме после него запускается согласованная последовательность двух ответов. В одиночной игре нет обязательной очереди/срока — пользователь добавляет моменты когда захочет.

### 25.3. Источник реплик — отдельный JSON, загрузка и отсутствие базы

- Соседний файл `lifegame_happiness_200_messages.json` — **база v1: 200 сообщений и 20 вымышленных персонажей**, с уникальными ID `happiness-NNN`, именами и текстами. Она **не встраивается в `index.html`**, не содержит персональные записи и **не входит** в JSON-резервную копию прогресса.
- При запуске на `http:`/`https:` функция `happinessAutoLoad()` запрашивает `./lifegame_happiness_200_messages.json`; при открытии `file://` автозагрузка не запускается, выбор локального файла доступен в настройках (`happinessManualLoad()`). При недоступной базе **одиночная игра остаётся возможной**, а отправка хода в виртуальном режиме требует подключённой базы. Для публикации через GitHub Pages файл JSON нужно размещать рядом с `index.html`.
- `happinessCheckLibrary()` строго проверяет версию 1, ровно 200 реплик/20 персонажей, уникальные ID и имена, ограничения текста. Состояние загруженной базы (`happinessLibrary`) временное; оно **отдельно от основного `state`**. Не обещать, что файл автоматически читается в любом браузере с `file://` или что он был опубликован: публикация отдельно не подтверждена.

### 25.4. Личная коллекция, редактирование, экспорт, сброс

- Собственный обычный ход немедленно сохраняется и в `chat`, и в `collection`; виртуальная реплика **не** сохраняется в коллекцию автоматически. Нажатие `♡/♥` создаёт/удаляет собственную копию этой реплики; удаление с подтверждением. В коллекции хранятся `source` (`self|virtual`), автор, редактируемый текст и `sourceChatId` — связь с исходной репликой. **Редактирование копии не изменяет сообщение в чате**.

- `state.happiness = { version:1, mode:"solo", collection:[], chat:[], usedIds:[], pending:null }` — новое поле в прежнем основном `state`, **без нового ключа localStorage**. `happinessDefaults()` задаёт пустое начало, `normalizeHappiness()` добавляет отсутствующее поле старым копиям и проверяет структуру.
