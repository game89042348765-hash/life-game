# Сквозные сценарии и контрольные точки

Сценарии описывают текущие механики. Их наличие не означает, что все эти шаги нужны в новой первой версии. Проверки здесь — будущие критерии сохранения поведения; фактически выполненные в этой подготовке проверки перечислены в README и runtime-schema.json.

## 1. Первый вход и возвращение

Пустое хранилище → emptyState → нормализация/миграции этапов → стартовые8 блоков и12 системных размещений → текущая локальная дата → экран Главной. Заданий/целей/личного времени нет. Служебная инициализация демонстрационных ништяков имеет собственный маркер и не должна повторно создавать набор при каждом посещении. Заставка и её повторный просмотр — отдельный жизненный цикл.

Возвращение → чтение сохранённого snapshot → normalize → ensureDay → восстановление активного таймера по его времени/статусу → render. Нельзя считать отсутствие виджета причиной удалить его данные или остановить подход.

Отказ чтения/повреждение → сообщение, блокировка записи, возможность забрать последнюю исправную копию. Не silently-emptyState поверх испорченного прогресса.

## 2. Из направления в обычное действие

Блок → текущий этап → смысл и цели → создать задание → указать награду/дни/тег/включение в Конструктор → валидация block/stage/goal/date → одна сохранённая task → актуальный план.

Создание само не выполняет действие, не достигает цель и не приносит деньги. Для разового «в Конструктор» записывает dayPlans; для повторяемого — inDayBuilder. Если создаётся дело будущего этапа, нельзя незаметно включить его как доступный текущий шаг. Смена даты/этапа во время формы отклоняет устаревшее включение, сохраняя ввод.

## 3. Быстро зафиксировать мысль

Быстрое добавление → название → без даты/сегодня/календарная дата → необязательный блок → 0/25 монет → Добавить.

Без даты: once в виртуальном inbox или в выбранном текущем этапе. Сегодня: разовое входит в план даты. Конкретная дата: calendarEntry вместо дублирующего task. После успешной записи черновик сбрасывается; при ошибке остаётся. Перенос позднее в блок сохраняет ID и историю. Выбор даты в мини-календаре до Добавить остаётся черновиком.

## 4. Собрать день и выделить главное

Найти задание → включить в план → проверить расписание/активность этапа/daySkip → выбрать главным из доступного сегодняшнего плана → mainDayTasks[дата].

Избранность и leadsToGoal не делают задание главным. Главное не добавляет само себя в план. Выбор одного главного не создаёт keyAction. После выполнения метка остаётся сегодня; завтра нужен новый явный выбор. Если действие выпало из доступного плана, текущий выбор может очиститься; исторический выбор не переписывается.

## 5. Попробовать начать и записать время

Главное/Шаг к цели/Первый шаг → выбранный доступный taskId → свободный общий focus → подход со снимком названия → running → paused/resumed или completed → явная форма подтверждения.

Вариант A: записать минуты без keyAction → focusLog recorded без actionId. Вариант B: выбрать активное keyAction → entries + дневные conditions + возможная выплата + focusLog-связь. Вариант C: пропустить → focusLog skipped,0 минут. Все варианты закрывают результат и защищают ID от повторной записи.

Запуск, окончание и запись минут **не выполняют task**. Выбор другого главного не переназначает существующий таймер. Запись связанного времени учитывается в итогах через entries, не прибавляется второй раз из квитанции.

## 6. Выполнить дело и отменить ошибку

Карточка в блоке/Конструкторе → toggleTask → актуальный ID и состояние архива/этапа → addRecord с текущими датой/reward/taskType → возможная сверка дневного бонуса → проверка балансов/normalize → localStorage → render → эффект звезды/счётчика/звука.

Повторное нажатие на выполненное инициирует отмену фактической записи, при необходимости подтверждение изменения денег. Оно не использует нынешнее значение награды вместо прежнего. Потраченный заработок блокирует отрицательный итог; отменяется вся операция, а не её часть.

Нулевая награда всё равно имеет факт task-выполнения и должна влиять на выполнение плана. Календарь с0 использует отдельный факт без монетной записи — это другое внутреннее представление того же пользовательского «сделал».

## 7. Закончить этап / подготовить следующий

Все этапы → будущая карточка/редактор → имя/описание/смысл/цели/дела → проверка блокировок и зависимостей → явный переход → новый current, reached=true → при отдельном подтверждении прежний passed=true.

Не происходит автоматического завершения целей или выплаты. Незавершённые дела прежнего этапа не удаляются. Предпочтения повторяемых сохраняются, но неактивный этап ограничивает их участие в дне. Выполненное сегодня остаётся в дневной истории. Возврат не стирает историю reached. При running/paused связанном подходе переход в том же блоке блокируется.

Стили «этап выполнен/стрелка далее» менялись отдельно от глубинного перехода. При новом обсуждении нельзя по скриншоту делать вывод, что галочка уже является полноценной универсальной машиной переходов.

## 8. Продвинуть квест

Создание counter/stages → настроить промежуточную/финальную награду → showInDay по желанию → шаг/этап → сохранить фактическое продвижение и ссылку на выплату → по достижении отдельный финал.

Изменение будущего stepReward не переоценивает прошлое. После начала target счётчика и состав/порядок stages защищены. Откат снимает конкретный последний шаг/этап и связанные выплаты, соблюдая баланс. Старый progress без подтверждённой подробной истории не даёт произвольной возможности «открутить» его как свежие оплаченные шаги.

## 9. Достичь цели и получить личный бонус

Выполненные связанные задачи → пользователь отдельно оценивает достижение цели → toggleGoal → completedDate + diamondRecords. В обычной карточке соответствующий footer скрыт; обработчик доступен в goalStep. Это надо решить явно при перепроектировании.

Магазин отдельно: выбрать товар/«Мою награду» → проверить цену, валюту, остаток, архив и отсутствие активной покупки → purchase-снимок → списание. Связи «пройден этап → автоматически выдать товар» в рабочей версии нет. Возврат использует сохранённую цену/валюту, а не новую редакцию товара.

## 10. Облегчить и закрыть день

Оценки минут + бюджет → read-only расчёт нагрузки → предпросмотр → подтверждение выбранных переносов → актуальная дата/snapshot → daySkips/dayPlans/planReviews. Для todaySkip повторяемое расписание на всю неделю не переписывается.

Вечерний итог → необязательные тексты → keep/tomorrow/later по незавершённым задачам → единая запись решений и переносов. Повторное сохранение не создаёт дублей. Календарь/квесты не переносит этот обработчик. Несохранённый старый черновик после полуночи не должен молча применяться к новому дню.

Итоги/недельный ритм пересчитываются из фактов: планы, намерения и запущенный таймер не равны записанному результату. Несколько фактов одной даты дают один результативный день, отдых не штрафуется.

## 11. Убрать лишнее и вернуться

Убрать виджет → удалить только размещение, данные остаются. Скрыть в дне → showInDay=false, сборка/инструмент остаются. Архив задания → archivedAt + очистка актуального/будущего плана, прежняя история остаётся. Восстановить → карточка доступна, но не включается в план автоматически. Архив блока распространяет недоступность на его содержимое.

Явное удаление keyAction/его времени и удаление календарной записи имеют специальные финансовые/исторические правила. Не применять к ним общий шаблон физического удаления всех связанных записей.

## 12. Отправить AI только разрешённый контекст

Открыть AI → временно ввести ключ/провайдера/модель → отдельно включить разрешения → увидеть whitelist JSON → подтвердить точную строку → запрос → ограниченный безопасный Markdown.

При изменении контекста/прав подтверждение требуется заново. AI не записывает задачи и не управляет журналом. Ключ и сообщения не входят в прогресс/URL. Реальная отправка и стоимость провайдера не проверялись при подготовке этой описи.

## 13. Сохранить переносимость новой версии

Перед новым проектированием нужны ответы не только «какие экраны», но и: какие ID/факты храним, что считается действием, когда выдаём награду, как отменяем, какой день авторитетен, что происходит при конфликте/отказе/смене этапа, как читаем старую копию. Для каждого принятого изменения в 04-COMPARISON.md предусмотрены эти поля.

Обязательность сохранения старого JSON пока **не решена**. До решения не пишем новый importer и не обещаем безусловную совместимость. Рабочий браузерный прогресс не использовался в этой подготовке.
